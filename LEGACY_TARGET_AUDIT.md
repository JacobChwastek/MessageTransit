# Legacy target and conditional code audit

This audit specifies the cleanup needed for MessageTransit runtime packages to support .NET 10 exclusively. It records the pinned pre-migration source baseline and its keep, simplify, or delete dispositions. Its tables remain historical audit evidence after implementation; current targets and declared dependencies are recorded in the [project inventory](docs/architecture/dependency-inventory.md). This audit does not establish build or test results.

The source baseline is [f78227eba](https://github.com/JacobChwastek/MessageTransit/commit/f78227eba59bfc20a3cea9c4ba2dd9e201de37be). It contains 59 tracked projects: 32 runtime libraries, one analyzer, 24 test suites, and two benchmark executables. Seven tracked `.props` files contain shared build configuration; there are no tracked `.targets` files. The source uses `MassTransit` names pending the coordinated [namespace and wire migration](NAMESPACE_AND_WIRE_MIGRATION.md).

## Target policy

| Project category | Planned target | Treatment |
| --- | --- | --- |
| All 32 runtime source projects | `net10.0` | Retain integration scope and remove older targets, including Windows-only `net472` appends. |
| Analyzer assembly | `netstandard2.0` | Keep as a compiler tooling asset in `analyzers/dotnet/cs`; it does not extend runtime package support. |
| All 24 test suites and two benchmarks | `net10.0` | Include projects outside the solution; verify both test execution and benchmark startup. |
| EF6 adapter and its tests during transition | `net10.0` | Retain the EF6 dependency temporarily for behavior comparison with EF Core. Provider compatibility and eventual adapter retirement require separate verification. |

The EF6 adapter currently targets `netstandard2.1` and appends `net472` on Windows while referencing the core project. Those targets cannot consume a `net10.0` core. Retarget the adapter with the other runtime libraries. If EF6 restore or provider behavior fails on .NET 10, perform parity comparisons against an isolated, pinned pre-retarget baseline rather than add old targets back to the public core. Retargeting is not approval to publish the transitional adapter.

Keep the analyzer's `netstandard2.0` target. Roslyn's [RS1041 guidance](https://github.com/dotnet/roslyn/blob/main/docs/roslyn-analyzers/rules/RS1041.md) explains that compiler extensions must be loadable in compiler execution environments independent of an application's runtime target. The analyzer currently references Roslyn Workspaces 4.11.0 with private assets and does not ship a normal `lib` assembly. Preserve that packaging and choose compiler-host support explicitly; validate loading, diagnostics, and code fixes in an SDK 10 consumer and each supported IDE host. Its test process can target `net10.0` independently. This choice does not promise support for older application runtimes.

Compatible third-party dependencies may supply .NET Standard assets to a .NET 10 consumer. Inspect their selected assets and runtime behavior; their implementation target does not itself mean MessageTransit supports an older runtime. Do not force every dependency's package major version to 10.

## Source branch rules

The tracked C# source contains 248 real conditional groups in 115 files, with 105 `#else` branches and no `#elif`. Two apparent groups in the expression compiler's block comment are documentation, not active directives. Include BOM-prefixed directives when counting. Each location is listed below; its disposition applies to its complete nested group, including the inactive alternative.

For `net10.0`, positive `NET5_0_OR_GREATER`, `NET6_0_OR_GREATER`, `NET8_0_OR_GREATER`, and `NET6_0_OR_GREATER || NETSTANDARD2_1_OR_GREATER` expressions are true. `NETFRAMEWORK`, `NETSTANDARD2_0`, `NETSTANDARD2_1`, and exact `NET6_0` are false. `!NET10_0_OR_GREATER` is false. Microsoft's [preprocessor reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/preprocessor-directives) distinguishes exact target symbols from `_OR_GREATER` symbols and states that .NET Standard symbols are not defined merely because a runtime implements .NET Standard.

Simplify a framework group by retaining the .NET 10 branch and removing its guard and obsolete alternative. Preserve nested feature/debug groups inside the retained branch. Delete a scope only where the entire helper is excluded on .NET 10. Keep provider, debug, hardware capability, and product behavior conditions where they remain meaningful.

The resulting source dispositions are **149 simplify, 12 delete, and 87 keep**. The delete set comprises ten nullable-attribute polyfill files, the inactive async-enumerable helper, and one .NET Framework-only IL emission block. The eleven uses of the nullable compatibility condition include `MemoryMessageBody`, where the selected span implementation must remain.

## Implementation verification sequence

1. Retarget all runtime and test/benchmark projects together, preserving the analyzer tooling exception. Evaluate every project, including outside-solution projects, on Windows and Linux. Check each project reference for a compatible target.
2. Simplify framework-based dependency selection, align EF Core providers, and remove compatibility references only after evaluating every consumer. Restore from a clean SDK 10 environment and review dependency warnings rather than suppress them.
3. Apply the source dispositions one behavior family at a time. Run the relevant existing suites identified below; use focused regression coverage where existing tests do not verify the changed semantics. Keep public helper behavior and third-party notices intact.
4. Pack all intended candidates and inspect framework assets, dependency IDs, analyzer placement, and legal metadata. Runtime libraries must contain only the intended .NET 10 assets; analyzer tooling remains separate.
5. Load the packaged analyzer in a clean .NET 10 consumer, verify diagnostics and code fixes, and exercise all declared compiler hosts. A unit test instantiating an analyzer does not prove package loading.
6. Repair CI and the developer container to execute this matrix. Record unavailable service tests explicitly and exercise benchmark startup independently from `dotnet test`.

Property/item evaluation establishes target selection and conditional references. It does not prove restore, compilation, package contents, runtime compatibility, database parity, or CI execution. Those checks belong to the implementation and release validation.
